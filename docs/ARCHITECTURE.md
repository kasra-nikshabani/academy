# ARCHITECTURE — SEPahan Academy OS

> وضعیت: Phase 0 اجرا شده. لایه‌ها برپا هستند اما فقط با یک مسیر نمونه (Health) پر شده‌اند.

## 1. تصمیم بنیادی

**Modular Monolith** روی Next.js. Backend و Frontend در یک Repository و یک Deployment واحد هستند.

Microservice ساخته نمی‌شود. دلیل: تیم کوچک، دامنه به‌هم‌پیوسته، و نیاز به Transactionهای چندجدولی (مثل پذیرش Tryout) که در معماری توزیع‌شده پرهزینه می‌شوند.

Java/Spring در این پروژه استفاده نمی‌شود. (پروژه `sepapp` باشگاه جداست و صرفاً از طریق API/SSO با این سیستم مرتبط خواهد شد، نه از طریق اشتراک کد.)

## 2. لایه‌ها

```
Presentation   app/**, components/**      ← Server Components پیش‌فرض
      ↓
API            app/api/v1/**/route.ts     ← Thin؛ فقط Parse + Authorize + Delegate
      ↓
Service        lib/services/**            ← تمام Business Logic
      ↓
Repository     lib/repositories/**        ← فقط Data Access
      ↓
Prisma         lib/db.ts → PostgreSQL
```

جریان هر Request:

```
Request → Validation (Zod) → Authorization (Permission + Scope) → Service → Repository → Prisma → Response Envelope
```

## 3. قواعد وابستگی (توسط ESLint enforce می‌شوند)

| قاعده | پیاده‌سازی |
|---|---|
| UI و Route Handler حق Import کردن `@/lib/repositories` یا `@/lib/db` را ندارند | `eslint.config.mjs` → `academy/layer-boundaries` |

این قواعد عمداً در ابزار قفل شده‌اند تا رعایتشان به Code Review وابسته نباشد.

## 4. مسئولیت هر لایه

### Route Handler
- Body/Query را با Zod Parse می‌کند
- کاربر جاری را resolve می‌کند
- Service را صدا می‌زند
- خروجی را در Envelope استاندارد برمی‌گرداند

**نباید:** شرط کسب‌وکار داشته باشد، مستقیم به Prisma بزند، یا Permission را خودش محاسبه کند.

### Service
- ورودی معتبر را می‌گیرد (فرض می‌کند Validation انجام شده)
- Permission **و** Scope را enforce می‌کند
- چند Repository را هماهنگ می‌کند
- عملیات چندجدولی را در Transaction می‌پیچد
- برای عملیات حساس AuditLog می‌نویسد
- `AppError` پرتاب می‌کند؛ هرگز `Response` نمی‌سازد

**نباید:** `next/server` را Import کند یا مستقیم Cookie بخواند.

### Repository
- Query می‌زند و داده خام برمی‌گرداند
- فقط فیلدهای لازم را Select می‌کند (پرهیز از N+1 و Over-fetch)

**نباید:** Permission چک کند، تصمیم کسب‌وکار بگیرد، یا Audit بنویسد.

### دو نکته درباره Prisma 7 و pg

**`$queryRaw` برای `pg_advisory_xact_lock` کار نمی‌کند.** خروجی `void` است و Adapter آن را به `UnsupportedNativeDataType` تبدیل می‌کند؛ باید `$executeRaw` استفاده شود.

**هر Query ای که به چند Statement تبدیل می‌شود و داخل یک Transaction اجرا می‌شود، باعث هشدار `client.query() while already executing` در `pg` می‌شود** — هشداری که در `pg@9` به خطا تبدیل خواهد شد.

> **این توضیح در Phase 11 اصلاح شد.** در Phase 8 فکر می‌کردم شرط لازم، وجود `$executeRaw` داخل یک Interactive Transaction است. اندازه‌گیری در Phase 11 نشان داد شرط واقعی گسترده‌تر است: **Transaction لازم است، اما لازم نیست صریح باشد.** پریزما خودش هر نوشتن چندمرحله‌ای را داخل یک Transaction ضمنی می‌پیچد.

سه شکلی که اندازه‌گیری شد:

| الگو | نتیجه |
|---|---|
| `create` با `include` سنگین (چند Relation یا `_count`) | **هشدار** — Transaction ضمنی پریزما |
| `$transaction([findMany با include، count])` | **هشدار** — همان دو Query با `Promise.all` هشدار نمی‌دهد |
| `create`/`findMany` تنها، بدون Transaction | سالم |

راه‌حل یکسان است: **داخل Transaction فقط ستون انتخاب کن، و رابطه‌ها را بعد از Commit بخوان.** برای فهرست‌های صفحه‌بندی‌شده، `Promise.all` به‌جای `$transaction([…])` (`lib/repositories/transaction.ts`).

### یک نکته عملیاتی

پس از هر `prisma migrate` + `generate`، **Dev Server را دوباره راه‌اندازی کنید.** فرایند در حال اجرا نسخه قبلی Prisma Client را در حافظه نگه می‌دارد و مدل‌های جدید به‌صورت `undefined` ظاهر می‌شوند. این در Phase 2 و Phase 3 هر دو بار اتفاق افتاد.

### Recharts آمد — با اندازه‌گیری، نه با فرض

Recharts از فاز ۱ برای این فاز کنار گذاشته شده بود و حالا استفاده‌کننده واقعی دارد. سه چیز اندازه گرفته شد:

۱. **۱۸ بسته، حدود ۳۵۰ کیلوبایت.** فقط صفحه‌ای که واقعاً نمودار دارد آن را بارگذاری می‌کند — با بررسی `client-reference-manifest` تأیید شد که فهرست تیم، تمرین و مسابقات هیچ‌کدام آن را نمی‌کشند.

۲. **با `next/dynamic` بعد از کاشی‌های آمار می‌آید.** کاشی‌ها همان چیزی هستند که بیشتر خواننده‌ها برایش آمده‌اند؛ نگه‌داشتن پاسخ پشت تصویرِ پاسخ، معامله بدی است.

۳. **ثابت‌های پالت از `chart.tsx` جدا شدند.** آن فایل `"use client"` است و Recharts را وارد می‌کند؛ وقتی جدول تیم — یک Server Component — فقط یک رنگ خواست، کل کتابخانه به سرور کشیده شد و صفحه در زمان ارزیابی ماژول شکست. `chart-palette.ts` بدون هیچ‌کدام، همین را حل می‌کند.

پالت Placeholder فاز ۱ با Validator سنجیده شد و چهار بررسی را رد کرد. مهم‌ترینش: **کنتراست `chart-1` روی کارت ۱.۵۲:۱ بود** — طلای نشان باشگاه به‌عنوان خط روی زمینه روشن تقریباً نامرئی است، همان نقصی که دکمه `outline` در فاز ۱۰ داشت.

### شش سنجه، پنج اسلات

`chartSlot` بیرون از پالت بی‌صدا به اسلات اول برمی‌گردد. شش سنجه در برابر پنج اسلات یعنی «قد» و «تست کوپر» یک نمونه‌رنگ گرفتند. هیچ خطایی پرتاب نشد و هیچ تستی نشکست — **روی صفحه دیده شد**. اسلات ششم ساخته و سنجیده شد، و تستی اضافه شد که یکتایی این نگاشت را تضمین می‌کند.

Recharts در مختصات SVG می‌کشد و `dir="rtl"` آن را برنمی‌گرداند، پس محور مقدار پیش‌فرض در `x=40` روی نموداری به عرض ۶۳۱ پیکسل می‌نشست — انتهای چپ صفحه‌ای راست‌به‌چپ. محور زمان اما چپ‌به‌راست ماند: زمان جهت نوشتار نیست.

### قاعده‌ای که فقط در یک نقطه بررسی می‌شد

`createAnnouncement` فرستنده Scope‌دار را از مخاطب سراسری منع می‌کرد. `publishAnnouncement` نمی‌کرد — و انتشار تنها مرحله‌ای است که واقعاً به کسی می‌رسد.

نتیجه: مربی نمی‌توانست اطلاعیه سراسری بنویسد، اما پیش‌نویس سراسریِ مدیر در فهرستش بود، با دکمه «انتشار» کنارش، و دکمه کار می‌کرد.

با باز کردن صفحه به‌عنوان مربی پیدا شد، نه با تست. حالا یک `assertMayAddress` مشترک هر دو مسیر را می‌بندد، `canPublish` همان را برای دکمه جواب می‌دهد، و سه تست قفلش می‌کنند.

> **درس عمومی‌تر:** وقتی یک عمل به «نوشتن» و «فرستادن» تقسیم می‌شود، قاعده مجوز باید روی **هر دو** بنشیند. نیمه دوم آن است که پیامدی دارد.

### دوباره همان تله pg

`update` با `select`، و `create` با `include` روی چند رابطه، هر دو به نقشه چندجمله‌ای Compile می‌شوند؛ Prisma آن را در Transaction ضمنی می‌پیچد و Adapter جمله بعدی را روی Client مشغول می‌فرستد. همان یافته Phase ۱۱، همان راه‌حل: `updateMany` برای شمارش گیرنده، و ساختِ خالی + خواندن دوباره برای اطلاعیه.

این بار Warning در خروجی تست دیده شد؛ ارزش دارد که `Errors 1 error` و `DeprecationWarning` هیچ‌وقت نادیده گرفته نشوند (PROJECT_RULES §۶.۱).
