# PRODUCT_SPEC — SEPahan Academy OS

## 1. هدف

سامانه جامع مدیریت آکادمی باشگاه فولاد مبارکه سپاهان: مدارس ورزشی، تیم‌های پایه، بازیکنان، والدین، کادر فنی، استعدادیابی، تمرین، حضور و غیاب، مسابقات، ارزیابی، عملکرد، اسناد، اعلان و گزارش.

سیستم از ابتدا **چندرشته‌ای** و **چند رده سنی** طراحی می‌شود.

## 2. ساختار آکادمی

```
Sport (مثلاً فوتبال)
 ├── AgeGroup: نونهالان، نوجوانان، جوانان، امید
 ├── School: مدرسه فوتبال
 └── Team: U12، U14، U16، U18، U21
```

همین ساختار باید بدون تغییر مدل برای رشته‌های دیگر کار کند.

## 3. نقش‌ها

| نقش | کار اصلی |
|---|---|
| Admin | کنترل کامل سیستم و تنظیمات |
| Academy Manager | مدیریت عملیاتی، تصمیم‌های استعدادیابی، گزارش |
| Staff / Coaching Staff | تمرین، حضور و غیاب، ارزیابی — فقط تیم‌های خودش |
| Main Team Player | اطلاعات شخصی، تیم، تمرین، عملکرد |
| School Player | نسخه محدودتر پنل بازیکن |
| Parent | فقط اطلاعات فرزندان خودش |

## 4. مسیر بازیکن

```
Registered → School Joined → Tryout Registered → Screening
          → Evaluation → Tryout Accepted → Team Joined → Promoted/Transferred
```

این Timeline در پروفایل بازیکن نمایش داده می‌شود.

## 5. جریان Tryout — ✅ پیاده‌سازی شد (Phase 10)

**عمومی:** فهرست Tryout → جزئیات → ثبت‌نام → OTP → اطلاعات فردی → اطلاعات ورزشی → ولی → مدارک → مرور → ثبت → شماره پیگیری → پیگیری وضعیت

**مدیریتی:** Screening → Evaluation → Decision

> مرحله **مدارک** به Phase 18 (Documents) موکول شد و در جریان فعلی وجود ندارد؛ لایه Storage هنوز ساخته نشده و یک مرحله آپلود ساختگی بدتر از نبودنش بود. مرحله **Evaluation** در Phase 11 پر می‌شود؛ الان درخواست پس از تأیید غربالگری به وضعیت `EVALUATION` می‌رود و منتظر تصمیم می‌ماند.

**شاخص‌ها:** Tryout فعال، تعداد درخواست، در انتظار Screening، ارزیابی‌شده، پذیرفته‌شده

## 6. تمرین

هر جلسه شامل: تیم، تاریخ، ساعت، مکان، نوع، برنامه، تمرین‌ها، بازیکنان، حضور، یادداشت و ارزیابی.

انواع: Technical · Physical · Tactical · Recovery · Mixed · Other

## 7. مسابقه

شامل: حریف، تاریخ، ورزشگاه، خانه/خارج/بی‌طرف، وضعیت، نتیجه، ترکیب، آمار بازیکن، یادداشت.

وضعیت‌ها: Scheduled · Live · Completed · Postponed · Cancelled

## 8. پنل والدین

فرزندان · تمرین · حضور و غیاب · مسابقات · عملکرد · اعلان‌ها · پروفایل

والد هرگز نباید اطلاعات بازیکن دیگری را ببیند.

## 9. داشبورد — ✅ پیاده‌سازی شد (Phase 16)

**Academy Manager** — KPI: کل بازیکنان، بازیکنان مدرسه، بازیکنان تیم اصلی، Tryout فعال، درخواست‌ها، حضور، تیم‌ها، رشته‌ها.
نمودارها: رشد بازیکن، توزیع رشته، قیف استعدادیابی، روند حضور، هشدارها.

**Admin** — نمای سیستم + نمای آکادمی + شمارش‌ها + رشد + توزیع رشته + قیف استعدادیابی.

> **یک صفحه، نه پنج.** داشبورد از بخش‌هایی ساخته می‌شود که هر کاربر حق دیدنشان را دارد، چون یک کاربر می‌تواند چند نقش داشته باشد — مربی‌ای که ولی هم هست هر دو بخش را می‌بیند. دلیل کامل در `BUSINESS_RULES.md` §۲۱.

## 10. خارج از محدوده MVP

پرداخت · پیامک انبوه · Push Notification · اپلیکیشن موبایل · Storage ابری · یکپارچگی با سیستم‌های باشگاه.

معماری باید این‌ها را در آینده بپذیرد، اما در MVP ساخته نمی‌شوند. از Overengineering پرهیز می‌شود.
