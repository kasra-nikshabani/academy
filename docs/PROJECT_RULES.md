# PROJECT_RULES — SEPahan Academy OS

## 1. قواعد غیرقابل مذاکره

منبع اصلی: [`../CLAUDE.md`](../CLAUDE.md) §2. خلاصه عملیاتی:

- TypeScript strict؛ `any` غیرضروری ممنوع
- Business Logic فقط در `lib/services`
- Repository فقط Data Access
- Zod برای هر ورودی خارجی
- Authorization همیشه در Backend؛ UI کافی نیست
- Secret داخل Git ممنوع
- OTP/Token/PII در Log ممنوع
- رکورد تاریخی Hard Delete نمی‌شود
- عملیات چندجدولی حساس Transactional است
- Dependency جدید فقط با دلیل فنی مکتوب
- تغییر معماری فقط با تأیید

## 2. Definition of Done

یک Feature وقتی Done است که در صورت مرتبط بودن، همه این‌ها کامل باشند:

UI · Validation · Authorization · Scope · Service · Repository · API · Database · Tests · Audit · Loading State · Empty State · Error State · Responsive · Accessibility · Documentation

## 3. حلقه توسعه هر فاز

```
Understand → Inspect → Plan → Implement → Test → Review → Fix → Document → Commit → STOP
```

پیش از پایان هر فاز، این دستور باید سبز باشد:

```bash
pnpm verify      # typecheck + lint + test + build
```

و در صورت مرتبط بودن:

```bash
pnpm test:e2e
```

سپس گزارش داده می‌شود و کار تا تأیید فاز بعدی متوقف می‌ماند.

## 4. Git

شاخه‌ها:

```
main        نسخه پایدار
develop     یکپارچه‌سازی
feature/*   قابلیت جدید
fix/*       رفع اشکال
refactor/*  بازسازی بدون تغییر رفتار
```

Conventional Commits:

```
feat:  fix:  refactor:  test:  docs:  chore:
```

پیام Commit باید بگوید چه چیزی تغییر کرده و چرا — نه صرفاً نام فایل‌ها.

## 5. سبک کد

- نام‌گذاری فایل: `kebab-case.ts`؛ Component ها `PascalCase.tsx`
- Service ها فعل‌محور: `acceptTryoutApplication()`
- Repository ها داده‌محور: `findPlayerById()`
- هر Export عمومی که رفتار غیربدیهی دارد، یک کامنت کوتاه «چرا» می‌گیرد — نه «چه»
- Prettier تنها مرجع Formatting است

## 6. تست

## 6.1 قواعد تست

- **تست نباید داده مشترک Seed را تغییر دهد** مگر اینکه بلافاصله برگرداند. بهتر: Fixture خودش را بسازد.
- **Fixture ها باید واقعاً یکتا باشند.** مقدار مشتق از `process.pid` یکتا نیست — pid بازچرخش می‌کند و چند اجرا بعد به تعارض می‌خورد.
- **تستی که `skip` می‌شود، تست نیست.** اگر Fixture پیدا نشد، بساز.
- **بعد از هر تغییر، تست‌ها را چند بار پشت‌سرهم اجرا کن.** یک اجرای سبز، پایداری را ثابت نمی‌کند.
- **دو Promise ای که رد می‌شوند را هم‌زمان شروع نکن.** الگوی `const a = f(); const b = g(); await expect(a).rejects…; await expect(b).rejects…` دومی را برای یک Tick بدون Handler رها می‌کند و Vitest آن را Unhandled Rejection گزارش می‌کند — به‌صورت متناوب، بسته به اینکه کدام Query زودتر تمام شود. یکی‌یکی `await` کن.
- **گزارش `Errors  1 error` را نادیده نگیر، حتی وقتی همه تست‌ها سبزند.** Vitest خودش هشدار می‌دهد که ممکن است باعث نتیجه مثبت کاذب شود.
- **بعد از اجرای تست، شمارش‌های پایه دیتابیس را با قبل مقایسه کن.** بازیکن، تیم، کاربر، رویداد، جلسه تمرین، حضور و غیاب. اختلاف یعنی یک Fixture پاک نشده است.
- **در Fixture ها تاریخ را با `toISOString()` Bind کن، نه با `Date`.** `pg` و Prisma دو قرارداد متفاوت برای `timestamp without time zone` دارند (docs/DATABASE.md §۱۰).
- **درخواست مستقیم API در تست E2E را `poll` کن.** Dev Server ای که Playwright بالا می‌آورد Turbopack است و زیر چند Worker موازی گاهی اتصال Keep-Alive را می‌بندد؛ یک `ECONNRESET` حدود یک اجرا از چهار، تستی را می‌شکست که هیچ ایرادی نداشت. `expect.poll` این را می‌گیرد، و `page.goto` و Locator ها خودشان Retry دارند.
- **`findFirst` بدون `orderBy` در تست، قطعی نیست.** پستگرس ترتیبی تضمین نمی‌کند؛ یک تست که «اولین بازیکن Seed» را برمی‌داشت، گاهی یکی از متقاضیان استعدادیابی را برمی‌داشت و حدود یک اجرا از ده، روی تعارض می‌شکست. رکورد تست را با کلید پایدار انتخاب کن و شرطش را صریح بنویس.
- **تستی که روی بازیکن Seed رویداد می‌نویسد، باید آن را پاک کند.** ثبت ارزیابی یک رویداد `EVALUATION` روی Timeline می‌نویسد؛ تست ارزیابی این را برای دو بازیکن پاک می‌کرد و برای سومی نه — و شمارش پایه در ۲۷ اجرا از ۱۳ به ۳۶ رسید. حالا مجموعه بازیکنانِ لمس‌شده نگه داشته می‌شود.
- **بررسی دستی در مرورگر هم روی داده Seed می‌نویسد.** اگر هنگام بازبینی بصری چیزی را تغییر دادی، برش گردان — همان قاعده اول، که برای آدم هم صدق می‌کند نه فقط برای تست.
- **پاکسازی E2E هر جدولی را که Fixture می‌سازد باید بشناسد، نه فقط آنهایی که یادت مانده.** جاروی افراد در `global-teardown` داخل `Player` را نگاه می‌کرد؛ ولی‌های Fixture در `Guardian` بودند و از قلم افتادند. تا Phase 14 تعدادشان به ۱۲۹۴ رسیده بود و پرونده بازیکنِ Seed که همه تست‌های «ولی» سراغش می‌روند، ۵۵ ردیف «ولی» تکراری داشت. **بعد از هر فاز شمارش هر جدولی را که آن فاز لمس می‌کند بگیر، نه فقط جدول‌های خودش.**
- **تستی که «همه» را تغییر می‌دهد، ردیف‌های Seed را هم شامل می‌شود.** «خواندن همه اعلان‌ها» دقیقاً همان کاری را کرد که می‌گفت، و اعلان Seed در همان صندوق بود. حذف اطلاعیه‌های خودِ Suite ردیف‌های خودش را پاک می‌کند اما نمی‌تواند ردیفی را که نساخته «نخوانده» کند — و نتیجه این بود که Badge از اجرای دوم به بعد روی دیتابیس تازه خالی می‌ماند. **وضعیت را قبلش بردار و بعدش برگردان.** با نگاه کردن به صفحه پیدا شد، نه با تست.
- **یک ادعای منفی به‌تنهایی نمی‌فهمد که موضوعش ناپدید شده.** «از مربی پنهان است» وقتی کارت از صفحه حذف شد همچنان سبز ماند؛ جفت مثبتش («به مدیر نشان داده می‌شود») بود که رگرسیون را گرفت. **هر `toBeHidden` باید یک `toBeVisible` متناظر داشته باشد**، وگرنه فقط ثابت می‌کند چیزی وجود ندارد.
- **رابطه‌ای که عمداً Nullable است، Cascade ندارد.** `OtpCode.userId` برای شماره‌های ناشناس خالی می‌ماند (فاز ۲)، پس پاک کردن کاربر آن ردیف‌ها را نمی‌برد و هر ورود Fixture یکی جا می‌گذاشت. هر جا کلید خارجی اختیاری است، بپرس پاکسازی ردیف‌های بی‌والد با کیست.
- **تستی که دور یک Seed ناقص را می‌گیرد، نقص را پنهان می‌کند — و معمولاً رکوردی جا می‌گذارد.** یک تست وقتی شخصِ حسابِ Seed را پیدا نمی‌کرد، یکی می‌ساخت و پاک نمی‌کرد. نتیجه دوگانه بود: رکوردی که از فاز ۱۱ در دیتابیس ماند، و Scope خالی‌ای که هر ادعای «نمی‌تواند…» را بی‌معنا سبز می‌کرد. **اگر Fixture ای که لازم داری در Seed نیست، Seed را درست کن؛ دورش را نگیر.**
- **Fixture را با Seed مقایسه کن، نه فقط با خودش.** تست‌های عملکرد اول روی همان بازیکن Seed می‌نوشتند که چهار روز اندازه‌گیریِ Seed داشت — و چون روزهای تست از روزهای Seed قدیمی‌تر بودند، «آخرین اندازه‌گیری» درست‌کارانه همان Seed می‌ماند و تست می‌شکست. کد درست بود؛ انتخاب Fixture غلط بود. برای ادعاهایی درباره «آخرین»، بازیکنی بردار که Seed لمسش نکرده.

## 7. افزودن کامپوننت shadcn

```bash
pnpm dlx shadcn@4.21.0 add <component>
pnpm ui:fix
```

قدم دوم اجباری است: `shadcn add` کامپوننت را با `import { cn } from "cn"` می‌نویسد و یک Micro-package را به‌عنوان وابستگی Runtime برمی‌گرداند. `pnpm ui:fix` ایمپورت‌ها را به `@/lib/utils` برمی‌گرداند. اگر پکیج `cn` دوباره در `package.json` ظاهر شد، حذفش کنید.

## 8. وابستگی جدید

قبل از افزودن هر Package:

1. آیا با کد موجود یا کتابخانه فعلی حل می‌شود؟
2. آیا نگهداری فعال دارد؟
3. آیا حجم/سطح دسترسی آن توجیه دارد؟

دلیل انتخاب در [`ARCHITECTURE.md`](ARCHITECTURE.md) §6 ثبت می‌شود.

| Package | فاز | دلیل |
|---|---|---|
| `recharts` | ۱۴ | نمودار روند عملکرد. در Stack پروژه (CLAUDE.md §۳) بود و از فاز ۱ برای همین فاز کنار گذاشته شده بود. ۱۸ بسته و حدود ۳۵۰ کیلوبایت — به همین دلیل فقط در صفحه‌ای بارگذاری می‌شود که واقعاً نمودار دارد، و آنجا هم با `next/dynamic` بعد از کاشی‌های آمار می‌آید. `TalentFunnel` (فاز ۱۲) عمداً به آن منتقل نشد: چهار میله نسبی یک وابستگی را توجیه نمی‌کنند. |
